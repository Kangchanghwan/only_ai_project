## 0. 요약

| 항목 | 결정 |
|---|---|
| 같은 와이파이 | 지금과 같다. 휴대폰이 같은 네트워크 목록에서 PC를 찾으면 아무것도 하지 않는다 |
| 다른 네트워크 | 휴대폰이 기존 1:1 '연결' 요청(`pair:invite`)을 저절로 보낸다. 요청에는 QR 증명을 붙인다 |
| 인증 | QR에 서버가 모르는 비밀과 PC 키 지문을 넣는다. 양쪽이 자동으로 확인하므로 **그림 4개 비교를 생략**한다 |
| 사람이 누르는 것 | PC '수락' 1번. 휴대폰은 없음 |
| QR 수명 | 5분마다 새로 만든다. 직전 회차도 받아서 **최대 10분** 유효하다. 1회용이 아니다 |
| 서버 | **수정 없음.** 미리 만드는 방이나 그림 코드도 없다 |

### 0.1 명세(`clipboard-share-activation-plan.md` 6장)와 다른 점

| 명세 | 이 설계 | 이유 |
|---|---|---|
| 그림 코드(SPAKE2)를 쓴다 | 기존 1:1 연결 요청과 키 교환을 쓴다 | 그림 코드는 이미 있는 그룹 방에서만 열린다(`code:open`이 방 멤버를 검사한다). 혼자인 PC는 방이 없어서, 숨은 방을 만들거나 서버를 고쳐야 했다. 1:1 연결 요청은 이미 다른 네트워크로도 간다(서버가 `sameNetwork`를 실어 보내고, PC 요청 창에 '다른 네트워크' 배지가 있다) |
| 4초 기다린 뒤 판정 | 첫 기기 목록이 오는 즉시 판정 | 같은 네트워크 탭과 같은 규칙으로 정확히 판정할 수 있다 |
| 코드 하나로 1대 | 5분 회차, 여러 대 가능 | 사람이 들일지 정하는 일은 PC 수락이 맡는다. 1회용은 불편만 더한다 |
| `#pc=…&c=…` | `#/qc?…`를 `index.html`에서 GA보다 먼저 지운다 | `index.html`이 GA에 `location.href`를 그대로 넘겨서, 앱 코드에서 지우면 비밀이 `page_location`에 실린다 |

## 1. QR 주소

```
https://www.clipboardapp.org/?utm_source=qr&utm_medium=empty_state#/qc?s=<소켓 ID>&k=<이름표 키>&g=<회차>&x=<비밀>&f=<지문>
```

| 값 | 내용 | 비밀인가 |
|---|---|---|
| `s` | PC 소켓 ID. 연결 요청을 보낼 대상 | 아님. 전체 공유 목록에 이미 보인다 |
| `k` | PC 이름표 키(`adj-animal-suffix`). 소켓 ID가 바뀌었을 때 다시 찾기 | 아님 |
| `g` | 회차 ID(4바이트 난수). PC가 어느 회차의 비밀과 키로 확인할지 고른다 | 아님 |
| `x` | 회차 비밀(16바이트 난수, base64url) | **비밀**. `#` 뒤라 서버로 가지 않는다 |
| `f` | 회차 키 지문 = SHA-256(PC 회차 공개키)의 앞 16바이트 | 아님 |

- `utm_*`는 그대로 둔다. 그래서 `qr_arrive` 측정이 이어진다.
- 길이는 약 190자다. QR이 지금보다 촘촘해지므로 140px에서 휴대폰 카메라로 읽히는지 확인한다. 안 되면 160px로 키운다.

## 2. 흐름

### 2.1 PC (QR을 띄운 기기)

1. 혼자인 화면의 QR이 보이면 회차를 만든다. 모두 PC 안에서만 만들고 서버에는 등록하지 않는다.
   - 회차 ID, 비밀, 회차 키 쌍(기존 `pairCrypto.generateEphemeral`)
2. 5분마다 새 회차를 만들고 QR을 다시 그린다. 지금 회차와 직전 회차만 기억한다.
3. 탭을 숨긴 동안은 회차를 만들지 않는다. 돌아왔을 때 지금 회차가 5분을 넘었으면 새로 만든다.
4. 혼자 상태가 끝나도 회차는 10분 동안 기억한다. 그 사이에 사진을 찍어 간 사람도 연결할 수 있게 하기 위해서다.

### 2.2 휴대폰 (QR을 찍은 기기)

1. `index.html` 인라인 스크립트가 `#/qc?`를 `window.__csQrCode`로 옮기고 `history.replaceState`로 지운다. `takeSend`·`takeInvite`와 같은 방식이다.
2. 앱이 접속해 같은 네트워크 목록을 받는다. 내 소켓이 들어 있는 첫 목록에서 판정한다(`roomPresence`의 ready 판단과 같다).
   - 목록에 `s` 또는 `k`가 맞는 기기가 있으면 같은 네트워크다. 아무것도 하지 않고 비밀을 버린다.
   - 없으면 다른 네트워크다.
3. 다른 네트워크라면:
   - 이미 그 PC와 같은 방을 쓰면 그 방 탭으로 이동하고 끝낸다.
   - '다른 네트워크 기기' 묶음을 펼치고 그 PC를 맨 위에 둔다. 전체 공유 목록이 잘려 PC가 없으면 QR 정보로 줄을 만든다.
   - 안내 한 줄을 보여 준다: "QR을 찍은 PC가 다른 네트워크에 있어요. 연결 요청을 보냈어요. PC에서 수락해 주세요."
   - 연결 요청을 보낸다(2.3).

### 2.3 연결 요청과 자동 확인 (기존 v3 흐름 위에 얹는다)

| 단계 | 누가 | 내용 | 기존/새로 |
|---|---|---|---|
| 1 | 휴대폰 | 1회용 키를 만들고 `pair:invite {to: s, pk}`를 보낸다. `pk`는 `<휴대폰 공개키>~<g>~<증명>` 형식이다 | 이벤트 기존, 증명 새로 |
| 2 | 서버 | `pair:incoming {from, sameNetwork:false, pk}`를 PC에 전달한다. 문자열 길이(200자)만 검사한다 | 기존 |
| 3 | PC | `g`로 회차를 찾고 증명을 검사한다. 맞으면 그 회차 키를 응답 키로 쓴다 | 새로 |
| 4 | PC → 휴대폰 | 기존처럼 응답 키(`pk`)를 보낸다. 서버는 그대로 전달한다 | 기존 |
| 5 | 휴대폰 | SHA-256(받은 PC 키) 앞 16바이트가 `f`와 같은지 본다. 같으면 `confirm(true)`를 자동으로 보낸다(보낸 쪽은 수락 전에도 가능한 기존 기능). 다르면 취소한다 | 새로 |
| 6 | PC | 요청 창을 'QR로 연결 요청' 모드로 띄운다. 그림 대신 "QR을 찍은 기기예요"를 보여 준다. 수락은 기존 `respond(true, {same:true})`(수락 + 같아요 한 번에)다 | 화면 문구 새로 |
| 7 | 서버 | 둘만의 방을 만들고 양쪽이 `onRoomReady`로 그 방 탭으로 이동한다 | 기존 |

- **증명** = HMAC-SHA256(키: 회차 비밀, 내용: `"cs-qr-v1" ‖ g ‖ 휴대폰 공개키`)의 앞 16바이트(base64url)
  - 세션 ID는 요청을 보낸 뒤에야 알 수 있어서 넣지 않는다. 대신 휴대폰 공개키가 요청마다 새로 만들어지므로 요청마다 값이 다르다.
- **서버가 바꿔치기할 수 없는 이유**
  - 휴대폰 키를 바꾸면 증명이 맞지 않는다. 서버는 비밀을 모른다.
  - PC 키를 바꾸면 지문이 맞지 않는다.
  - 그래서 그림 비교가 하던 확인을 기계가 대신한다. SAS 계산은 기존 코드대로 하고 화면에만 띄우지 않는다.
- **같은 회차 키를 여러 요청에 쓰는 문제**
  - 세션 키는 `deriveSession`에서 휴대폰의 새 키와 세션 ID로 만들어진다. 그래서 요청마다 다르고, 서로의 연결을 엿볼 수 없다.

### 2.4 PC가 거절하는 경우

PC가 아래 경우를 만나면 `pair:signal {t:'qr', reason}`으로 이유를 먼저 보내고 기존 거절(`respond(false)`)을 한다. 휴대폰은 이유에 맞는 문구를 보여 준다.

| 이유 | 조건 | 휴대폰 문구 |
|---|---|---|
| `expired` | `g`가 지금이나 직전 회차가 아님(10분 지남, PC 새로고침) | "QR 시간이 지났어요. PC 화면의 QR을 다시 찍어 주세요." |
| `invalid` | 증명이 틀림 | 같은 문구 (조작 여부를 드러내지 않는다) |
| `busy` | 대기 중인 QR 요청이 이미 3개 | "PC에 요청이 많아요. 잠시 뒤에 다시 찍어 주세요." |

기존 거절이므로 서버의 30초 쿨다운이 그대로 걸린다.

## 3. 예외 상황

| 구분 | 상황 | 처리 |
|---|---|---|

| 판정 | 휴대폰이 와이파이와 데이터를 오가는 중 | 첫 목록으로만 판정한다. 열린 방은 그대로 둔다 |
| 판정 | 기기 목록이 5초 안에 오지 않음 | 아무것도 하지 않고 `error`로 기록한다 |
| 판정 | QR 스캐너 앱이 `#` 뒤를 버림 | 지금과 같이 동작한다. `utm_medium=empty_state`인데 `#`이 없으면 `no_hash`로 기록한다 |
| PC | 새로고침, 탭 닫힘 | 이름표 키로 새 소켓을 찾으면 그 PC가 `expired`로 거절한다. 못 찾으면 `TARGET_NOT_FOUND` → "PC를 찾지 못했어요. PC 화면의 QR을 다시 찍어 주세요." |
| PC | 탭이 뒤에 있거나 화면이 꺼짐 | 기존 60초 만료. "PC에서 수락하지 않았어요."와 다시 요청 버튼 |
| PC | 대기 중인 QR 요청 3개 초과 | `busy`로 거절 |
| QR | 다른 네트워크의 여러 명이 같은 QR을 찍음 | 요청이 차례로 뜨고 PC가 하나씩 수락한다. 같은 네트워크 사용자는 비밀을 쓰지 않으므로 영향이 없다 |
| QR | 10분이 지난 사진 | `expired` |
| QR | 증명이나 지문이 틀림 | 중단한다. 자동 '같아요'를 보내지 않는다 |
| QR | PC가 자기 QR을 찍음 (같은 기기, 같은 브라우저의 다른 탭) | 내 기기면 무시한다 |
| 관계 | 이미 같은 방을 씀 | 요청 없이 그 방 탭으로 이동한다 |
| 관계 | 차단됨, 30초 쿨다운 중 | 기존 문구 |
| 버전 | 운영 서버가 `pk`를 전달하지 않는 예전 버전 | PC는 증명 없는 보통 요청으로 받고 기존 그림 비교 흐름으로 이어진다. 구현 전에 운영 서버 버전을 확인한다 |
| 개인정보 | 비밀이 GA, 기록, 북마크로 샘 | `index.html`에서 GA보다 먼저 지운다. 비밀, 소켓 ID, 키, 회차는 어떤 이벤트에도 넣지 않는다 |

## 4. 측정

| 이벤트 | 매개변수 | 상한 |
|---|---|---|
| `qr_code_fallback` (새로 만듦) | `result`: `same_network`, `room_ok`, `declined`, `expired`, `busy`, `not_found`, `timeout`, `error`, `no_hash` | QR 도착 세션당 1회. 마지막 결과만 보낸다 |
| 기존 `pair_invite`, `pair_incoming`, `pair_done`, `connected_any` | 그대로 | 그대로 |

- **GA4 등록 필요**: `result`
- `pair_done`이 늘어나므로 PR B(방 연결 힌트)와 같은 주에 배포하지 않는다. QR로 생긴 연결은 `qr_code_fallback{room_ok}`로 따로 센다.
- 판정 목표: QR로 들어와 혼자 남는 비율 54% → 20% 이하, 같은 와이파이인데 방으로 넘어간 비율 5% 이하.

## 6. 테스트

- `qrLink`
  - 주소 만들기와 읽기가 서로 맞다. `utm_*`가 남는다.
  - 증명은 비밀이나 휴대폰 키가 하나라도 다르면 맞지 않는다.
- `index.html`
  - `#/qc?`가 GA `config` 전에 주소에서 지워진다. prerender 검사와 같은 방식으로 확인한다.
- `useQrArrival`
  - 같은 네트워크 목록에 `s` 또는 `k`가 있으면 요청을 보내지 않는다.
  - 없으면 그 PC 대상으로 `invite`를 1번 부른다.
  - 이미 같은 방이면 탭만 바꾼다.
  - 목록이 안 오면 `error`로 기록한다.
  - 측정은 세션당 1회다.
- `pairing`
  - 가짜 소켓 쌍으로 QR 요청 → PC 수락 → 방까지 간다. 휴대폰 쪽 confirm이 자동이다.
  - 직전 회차는 통과하고 그 전 회차는 `expired`로 거절된다.
  - 증명이 틀리면 `invalid`로 거절된다.
  - 서버가 PC 키를 바꾸면 휴대폰이 취소한다.
  - 서버가 휴대폰 키를 바꾸면 PC가 거절한다.
  - QR 대기 요청 4번째는 `busy`로 거절된다.
  - 증명이 없는 보통 요청은 기존 그림 비교 흐름 그대로다.
- `useQrHost`
  - 5분마다 회차가 바뀌고 직전 회차만 남는다.
  - 탭을 숨긴 동안은 만들지 않는다.
- 기존 `ConnectionCard.emptyState.test.js`
  - 새 주소에 맞게 고친다. `utm_*` 검사는 유지한다.
- 실제 확인
  - 로컬 서버와 두 탭으로 흐름을 확인한다. 다른 네트워크는 봇 소켓의 IP를 바꿀 수 없으므로 단위 테스트로 대신한다.
