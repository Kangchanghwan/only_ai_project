# P2P 직접 전송 도입 판단 기준 (2026-10-24 확정, 데이터 보기 전)

목표: 같은 방에 상대 기기가 접속해 있을 때 파일을 WebRTC로 바로 보내 "다 올린 뒤 받기"의 대기 시간을 줄인다.
전제: **다운로드 신뢰성은 지금보다 떨어지면 안 된다.** 그래서 R2 업로드·다운로드 경로는 그대로 두고, P2P는 추가 빠른 길로만 쓴다.

## 1단계: 측정 (이 PR, 화면·동작 변화 없음)
- `p2p_probe` v2: 직접 연결되면 LAN 8MB / NAT 2MB를 보내고 바이트 수·순서를 검증한다.
  `transfer` = complete | mismatch | stalled | closed | error | complete_legacy, `mbps_bucket`.
- `upload_perf`: 8MB 이상 업로드 성공 시 실제 R2 업로드 속도(`upload_mbps`, `mbps_bucket`, `upload_path`, `retries`, `resumed`).
- `upload_perf_fail`: 8MB 이상 업로드 실패(`reason`).
- 끄기: `VITE_P2P_PROBE_ENABLED=false` (probe만). upload_perf는 이벤트 전송만 하며 업로드 결과에 영향 없음.

## 판단 시점과 표본
- 배포 후 7일 판독. 표본이 모자라면 최대 14일까지 연장.
- 최소 표본: v2 probe 중 직접 연결 60건 이상(direct_lan 40건 이상), upload_perf 30건 이상.

## 통과 기준 (모두 만족해야 2단계 진행)
| # | 항목 | 기준 |
|---|---|---|
| C1 | 연결률 | 직접 연결 / 응답 받은 점검(got_answer=true) ≥ 85% |
| C2 | 전송 완료율 | transfer=complete / 직접 연결(v2) ≥ 97%, mismatch = 0건 |
| C3 | 속도 | P2P(direct_lan, complete) 중앙값 구간이 R2 업로드 중앙값 구간보다 1단계 이상 높음. 같은 구간이면 평균이 1.5배 이상 |
| C4 | 수요 | 7일간 upload_perf ≥ 30건 (큰 파일 전송이 실제로 있어야 효과가 있음) |

구간: <5, 5-20, 20-50, 50-100, 100-300, 300+ Mbps.
하나라도 미달이면 2단계는 하지 않고 숫자와 함께 보류 보고.

## 2단계 (통과 시): 그림자 모드 → 실제 적용
1. R2 업로드는 지금과 똑같이 항상 진행한다. 상대가 온라인이면 P2P로도 동시에 보낸다.
2. 그림자 모드(1주): 받는 쪽은 P2P 데이터를 1MB마다 SHA-256으로 검증만 하고 버린다. 저장은 지금처럼 R2.
   통과: 검증 일치율 ≥ 99.5%, P2P 완료가 R2 업로드 완료보다 빠른 비율 ≥ 70%.
3. 실제 적용: P2P가 끝까지 받아지고 모든 조각 해시가 맞을 때만 P2P 데이터로 저장. 하나라도 어긋나거나 끊기면 섞지 않고 R2로 받는다.
4. 킬스위치와 자동 중단: 실제 적용 후 P2P 저장 실패율 > 1% 또는 해시 불일치 1건이라도 나오면 끄고 R2만 쓴다.
